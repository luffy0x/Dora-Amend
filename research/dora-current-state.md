# Dora 公开现状研究 v0.1

更新时间：2026 年 8 月 28 日

## 1. 证据范围

本研究基于公开资料与用户授权登录后的只读界面观察：

- [比赛官网](https://finers2026.github.io/fanruan-UED-Challenge/)
- [Dora 官网](https://www.fanruan.com/dora)
- Dora 登录产品：`https://dora.fanruan.com/decision/dora/chat`

浏览器核验显示，Dora 官网的“立即体验”“观看视频”和“登录”入口均经过帆软通行证。用户已完成登录，本轮进入了 Dora 首页、Experts 列表、财务分析专家详情和 Resources 页面，并在用户明确确认后向系统自带的财务分析专家发送了一条推荐样例问题；未上传文件、收藏专家或修改其他产品数据。下文仍严格区分官网事实、登录界面观察、设计推断与待核验问题。

## 2. 已核验事实

### 产品定位

- Dora 定位为企业级 Data Agent 平台，而不是通用聊天机器人。
- 公开能力包括自然语言问数、归因分析、报告生成、指标推送和异常预警。
- 官网将经营指挥、门店业绩归因、市场洞察、供应链风险、证券财富运营和仪表板诊断列为业务场景。
- Dora 强调与 FineReport、FineBI 的历史指标、权限、报表与看板资产连接，并可对接 IM、API 和 MCP。

### 已有可信能力

- 官网明确宣称“每条数据结论附带推导路径”，并通过统一语义层降低口径歧义。
- 官网同时强调权限管理、执行审计、安全沙箱和 SQL 防注入。
- 赛题明确说明当前产品已经存在思考过程、工具步骤、SQL 明细和最佳实践引用。
- 赛题指出这些信息分散在会话和后台监控中，普通用户仍难以理解数据来源、更新时间、筛选条件、事实与推断差异，以及错误修正入口。

### 已核验的产品信息架构

- 顶部一级入口为 Dora、Experts 和 Resources，与赛题描述一致。
- Dora 首页左侧包含搜索、新建会话、定时任务和历史会话区域。
- 首页输入区支持上传文件和添加 FineBI 资产。
- 首页公开十类任务入口：数据探索、深度分析、归因诊断、趋势预测、分析报告、幻灯片、数据可视化、监控预警、指标管理和业务洞察。
- “数据探索”会展示可直接使用的示例问题，例如区域销售额及环比、商品销售 Top 10、库存周转天数异常。
- Experts 页面提供人力、资管、财务、考勤、零售会员和新能源经营等示例专家。
- “财务分析专家”绑定演示数据，公开描述覆盖财务查询、指标对比、异常归因、报告生成和风险预警，并提供利润率下降、区域预算等推荐问题。
- Resources 页面当前账号显示暂无资源。

### 已核验的回答体验

- 测试问题为“Q3 净利润率为什么比 Q2 下降了？”，来自专家欢迎语中的推荐示例。
- 执行结束后页面将过程收拢为“21 个行动、耗时 1 分 19 秒”的可展开区域。
- 展开后包含多段英文 Reasoning、任务说明、工具结果和 Python/SQL 命令，并提供复制、下载等操作。
- Agent 在多轮检查后发现演示数据仅覆盖 2026 年 3 月 29 日至 6 月 26 日，缺少 Q3 数据，同时缺少计算净利润率所需的标准财务科目。
- 最终回答正确选择了不生成无依据结论，说明缺少的数据并给出三个后续选项。
- 最终答案和推荐追问主要使用英文，而用户问题与专家介绍使用中文。
- 当前回答区域未观察到独立的数据来源、更新时间、筛选条件摘要，也未观察到事实/推断标签、就地纠错、影响预览或版本对比入口。
- “未观察到”仅代表本次异常样例与当前账号界面，不能推断所有成功回答均不存在这些能力。

### 视觉语言

- 公开官网以浅蓝、白色和高饱和蓝色作为主要色彩。
- 品牌呈现使用大字号标题、渐变蓝强调和轻量玻璃质感卡片。
- 登录产品使用浅灰背景、白色主工作区、深灰文字、低饱和蓝紫渐变强调，以及细描边圆角控件。
- 产品采用窄图标导航、可折叠会话侧栏与居中大输入框；整体强调留白和低视觉噪声。
- 当前界面同时出现英文导航/操作标签与中文专家内容；是否由账号语言或版本配置导致尚未核验，暂不作为设计问题。

## 3. 现状问题重述

命题暴露的不是“系统没有日志”，而是三类前台体验断层：

1. **信息组织断层：** 证据按执行过程组织，而用户围绕具体结论判断。
2. **角色语言断层：** SQL、工具步骤和后台监控服务于技术人员，普通业务用户需要数据范围、口径和来源。
3. **操作闭环断层：** 看见问题之后，用户仍不知道从哪里纠正以及纠正会影响什么。
4. **时机断层：** Agent 已在执行中发现数据缺失，但用户直到长流程结束才得到“当前无法可靠回答”的结论。

## 4. 对 Dora Amend 的直接约束

- 不能把“展示 SQL、来源或推导路径”本身包装成创新，因为 Dora 已有相关能力。
- 不能默认展开完整 Agent 行动链，避免把后台监控搬到前台。
- 必须围绕单条结论组织证据，并把修正入口放在用户发现问题的位置。
- 必须展示修正的影响范围和新旧差异，才能形成区别于“可追溯”的完整闭环。
- 目标是校准信任：帮助用户识别什么时候可信、什么时候需要怀疑，而不是单纯提升信任感。
- 必须把数据缺失、时间范围不覆盖等关键可靠性信号前置，并允许用户尽早补充或调整问题。

## 5. 尚未核验

- 成功生成业务结论时的回答布局、图表和长回答状态。
- 成功分析场景下 SQL 明细与最佳实践引用的具体呈现。
- 产品是否已经区分数据事实、模型推断和行动建议。
- 当前是否允许在结论处修改口径、筛选条件或数据源。
- 修改后是完整重跑还是可以局部重跑。
- 是否存在回答版本、差异对比和审计记录。
- 执行中、失败、无权限和数据过期等状态的呈现方式。

## 6. 给赛事助手的核验问题

1. 当前体验账号是否与比赛所描述的产品版本一致？
2. 普通业务用户目前从哪里查看一条结论对应的数据来源和更新时间？
3. 筛选条件和指标口径位于回答页、执行详情还是管理后台？
4. “思考过程”展示的是面向用户的执行摘要，还是模型内部推理文本？
5. 用户目前可以纠正哪些错误：问题表述、筛选条件、指标口径、数据源或最佳实践？
6. 纠正后系统是否保留原结论和修改记录？
7. Dora 是否支持只重跑受影响的步骤？
8. 原型需要严格遵循现有产品视觉系统，还是允许概念性重塑？

## 7. 当前结论

基于公开证据，Dora Amend 的差异化不应落在“更多透明信息”，而应落在：

> 以结论为中心压缩可信信息，并把追溯、修正、影响确认和结果对比连接为同一条业务闭环。

登录实测已经确认产品入口、任务类型、过程日志和一次“数据不足”的最终回答。该样例支持“可靠性信号需要前置、技术过程需要压缩、错误需要就地修正”的设计判断。成功结论场景仍需核验；如果后续实测显示已存在同等闭环，则必须调整创新重点。
