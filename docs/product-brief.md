# Dora Amend 产品立项简报

## 1. 项目定义

**一句话定位：** Dora Amend 是面向业务用户的“可信回答层”，让 Dora 的每条结论都能被快速理解、核验来源、定位问题并低成本纠正。

**产品主张：** 可信不是展示更多执行日志，而是让用户在需要时获得恰到好处的证据，并能把发现的问题直接转化为一次可控的修正。

**信任目标：** 项目追求的是“校准后的信任”，不是让用户无条件相信 AI。正确时用户知道依据，异常时用户能够发现、追溯并纠正。

**参赛命题：** Dora 赛道 · 命题 3：让 Dora 的每个结论都“看得懂、信得过、能追溯”。

## 2. 问题与机会

Dora 已经具备思考过程、工具步骤、SQL 明细和最佳实践引用，但这些信息分散在会话与后台监控中。普通业务用户面对结论时仍需解决四个问题：

1. 这句话是数据事实、Agent 推断，还是行动建议？
2. 使用了哪些数据，数据更新到什么时候，分析范围和筛选条件是什么？
3. 如果结论可疑，应该从哪里追溯，而不是阅读整段执行日志？
4. 如果口径或条件错误，能否直接修正并看懂修改造成的影响？

现有信息不是不足，而是缺少围绕“结论”组织的前台体验。项目机会是将分散的技术信息重组为业务用户可理解、可操作的可信链路。

## 3. 目标用户与演示场景

**核心用户：** 使用经营数据做判断、但不熟悉 SQL 和 Agent 执行机制的区域经营负责人。

**演示任务：**

> 为什么华东区 7 月利润下降？请给出主要原因和经营建议。

Dora 初次分析认为“上海门店客单价下降是主要原因”。用户核验后发现分析未排除 7 月新开门店，于是修正可比门店口径。Dora 在执行前提示受影响的事实和结论，完成局部重跑，并展示修改前后的结论差异。

选择该场景的原因：它同时包含数据时效、筛选范围、指标口径、事实与推断区分以及纠错重跑，能够在一条故事线中覆盖完整命题。

## 4. 体验目标

用户不阅读复杂日志，也能完成以下闭环：

```text
理解结论 → 判断可靠性 → 按需追溯 → 修正问题 → 确认影响 → 对比新旧结论
```

### 4.1 看得懂

- 将回答拆分为“数据事实”“Agent 推断”“行动建议”。
- 用自然语言解释指标变化和因果关系，技术细节默认收起。
- 结论先行，证据按需展开，避免将执行过程变成阅读负担。

### 4.2 信得过

- 在结论附近展示数据来源、更新时间、分析范围和关键筛选条件。
- 展示数据是否完整、口径是否一致、执行是否存在警告等客观状态。
- 不提供缺乏解释依据的单一“可信度分数”。

### 4.3 能追溯、能纠错

- 点击任一结论，只展开与该结论相关的证据、计算和工具结果。
- 允许用户通过自然语言或结构化选项修正时间、范围、指标口径和筛选条件。
- 重跑前提示影响范围，重跑后突出结论、数据与建议的变化。

## 5. 核心方案

### 5.1 结论可信摘要

默认态以最少信息回答“这次分析用了什么”：

- 数据截至时间；
- 数据来源数量与名称；
- 地区、时间、订单状态等关键范围；
- 是否存在缺失数据、口径冲突或执行警告；
- 回答中事实、推断和建议的明确标识。

### 5.2 结论级证据追溯

用户点击具体结论后，侧边证据视图仅展示该结论关联的内容：

- 原始指标与可视化；
- 数据表、字段和更新时间；
- 使用的筛选条件与计算口径；
- 相关 SQL、工具步骤和最佳实践引用；
- 从数据事实到 Agent 推断的关系。

该视图不展示模型隐藏的思维过程，只展示可审计的输入、系统动作、工具结果和业务证据。

### 5.3 就地纠错

每条结论旁提供“核验与纠正”入口。用户可以提出“排除新开门店”“利润应按含税口径计算”等修正，也可以直接编辑结构化条件。系统将自然语言修正转换为明确变更，等待用户确认。

### 5.4 影响预览与局部重跑

执行前告诉用户：

- 哪些数据范围或计算条件发生变化；
- 哪些事实、推断和建议将被重新计算；
- 哪些内容不会受到影响。

执行后通过新旧版本对比展示数值、原因排序和行动建议的变化，保留修正记录以便回看。

## 6. 原型范围

制作一个基于 React 的高保真交互原型，使用固定 Mock 数据与有限状态模拟 Agent 行为。核心页面和状态包括：

1. **对话与结论页：** 展示可信摘要以及事实、推断、建议。
2. **证据追溯视图：** 从单条结论查看数据、口径、筛选条件与执行步骤。
3. **纠错面板：** 将自然语言纠正转换为可确认的结构化修改。
4. **影响确认状态：** 展示即将重跑的范围。
5. **重跑过程状态：** 展示可理解的执行进度，不暴露冗长日志。
6. **版本对比状态：** 对比修改前后的事实、结论和建议。
7. **异常状态：** 数据过期、来源不可用、权限不足或修正存在歧义。

## 7. 明确不做

- 不实现真实数据库、Text-to-SQL 或生产级 Agent 编排。
- 不复刻 Dora 全部功能，不改造管理后台。
- 不把 SQL、工具调用或执行日志直接平铺给普通用户。
- 不把模型内部思维过程作为可信证据。
- 不用无法解释的百分比代表结论可靠性。
- 不伪造企业用户研究、真实业务数据或测试结论。

## 8. 验证计划与成功标准

使用任务型可用性测试邀请 5 名具备数据看板或数据分析使用经验的参与者；如果参与者并非企业经营负责人，在报告中明确标注为代理用户。

测试任务：理解结论、找到数据范围、区分事实与推断、发现口径问题、完成纠错并解释新旧结果差异。

目标指标：

- 80% 参与者能在 10 秒内找到数据截至时间和分析范围。
- 80% 参与者能正确区分数据事实与 Agent 推断。
- 80% 参与者能在无提示情况下完成一次口径纠正。
- 80% 参与者能正确解释修改后结论发生变化的原因。
- 记录完成时间、误操作点、理解偏差和主观信任变化，用于下一轮迭代。

以上均为设计目标，只有完成真实测试后才能写为验证结果。

## 9. 关键决策与风险

1. **可信摘要优先于完整链路。** 用户首先需要快速判断，而不是学习 Agent 的内部结构。
2. **结论级追溯优先于全局流程图。** 追溯入口与当前疑问保持上下文关联，降低理解成本。
3. **纠错闭环优先于只读解释。** 能修正错误比单纯看到错误更有业务价值。
4. **客观信号优先于可信度评分。** 可核验的信息比算法生成的分数更可信。
5. **前端交互原型优先于真实后端。** 评审重点是体验创新、易用性和方案完整性。

最脆弱的假设是业务用户愿意在看到异常时主动核验证据。为降低该风险，默认界面必须在数秒内提供可信摘要；完整证据链只在用户需要时展开。
