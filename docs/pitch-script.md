# Dora Amend 现场路演稿

建议主讲控制在 4 分 30 秒，留出时间处理设备切换或评委追问。

## 30 秒项目介绍

> Dora Amend 是给 Data Agent 增加的一层可信回答体验。它把数据来源、更新时间、分析口径和推断依据组织到每条结论周围。用户发现问题后，可以直接修正条件，先确认影响范围，再局部重跑并比较新旧答案。这个原型解决的不是“日志怎么展示”，而是业务用户如何判断一条结论能不能用于决策。

## 5 分钟主讲稿

### 00:00 至 00:30，从错误决策风险切入

> 屏幕上这份分析认为，华东区 7 月利润下降 18.7%，首要原因是上海门店客单价下降。它看起来很完整，也给出了经营建议。但分析中混入了 7 家开业不足 90 天的新店。如果负责人直接按这个结论调整促销，可能会解决错误的问题。

画面：停留在初始回答标题、可信摘要和“包含 7 家新店”的提醒。

### 00:30 至 01:00，说明用户为什么仍然难以信任

> Dora 已经提供思考过程、工具步骤、SQL 明细和最佳实践引用。普通业务用户面对一条结论时，这些信息仍然分散。他需要知道数据更新到什么时候、用了什么口径、这句话是事实还是推断，出了问题又该在哪里改。

> 我把交互中心从执行过程改成了结论。每条结论都成为一个可以核验、修订和比较的对象。

画面：指向可信摘要，再指向“数据事实”“Agent 推断”“行动建议”标签。

### 01:00 至 01:45，按结论查看证据

> 用户点击“客单价下降是首要原因”，右侧只呈现与这条推断有关的证据。这里既有客单价变化和贡献度计算，也提示新店与成熟门店被直接比较，相关性不等于已经证明因果。

> 业务用户看到的是事实、计算和口径提醒。查询编号、字段、Mock SQL 和引用关系默认收起，需要审计时再展开。

操作：点击客单价结论，展开“技术明细”，停留 3 秒后收起。

### 01:45 至 02:40，纠正条件并确认影响

> 发现口径问题后，用户不需要另开会话重述上下文。他可以在当前结论旁提出“排除开业不足 90 天的新店”。系统先把自然语言转换成明确条件，用户确认后才继续。

> 重跑前，影响预览列出即将变化的利润降幅、原因贡献和行动建议，同时说明数据来源、时间范围和订单状态不会改变。

操作：点击“核验并纠正”，展示结构化条件，生成影响预览。

### 02:40 至 03:35，局部重跑并比较版本

> 系统只重算受影响部分，并保留原回答。修订后，利润降幅从 18.7% 收窄到 8.4%，首要原因从上海客单价变为履约成本率，行动建议也转向即时配送定价和补贴。

> 用户看到的不只是两个不同答案，还能确认是哪项口径修改导致了变化，并随时回看 v1 的结论和证据。

操作：确认局部重跑，等待三步进度完成，展示版本对比并切换 v1、v2。

### 03:35 至 04:05，展示失败状态

> 可信也包括知道什么时候不能给结论。数据只更新到 7 月 29 日时，Dora Amend 会暂停完整月结论；门店主数据不可用或当前账号没有明细权限时，也会明确展示证据缺口。系统不会用不完整或无权限的数据补出一个确定答案。

操作：快速切换“数据过期”和“权限不足”，各停留 3 秒。

### 04:05 至 04:30，收束创新点与边界

> 这个方案用可核验信号替代缺乏解释的可信度分数，并把可信从只读说明推进到可纠正闭环。当前交付是 React 高保真原型，使用虚构 Mock 数据，不连接真实数据库或模型。我已经完成完整流程、异常状态和响应式验证，真实用户测试仍在计划中，后续只会引用有原始记录支持的结果。

> Dora Amend 希望让业务用户对 Agent 形成校准后的信任：依据充分时敢于采用，条件有误时能够发现并修正。

## 评委可能追问

### 这是不是 Agent 行动链可视化？

不是。行动链以系统执行过程为中心，Dora Amend 以用户正在判断的结论为中心。默认只展示来源、时间、范围、口径和事实与推断关系，技术执行细节按需展开。

### 为什么不用可信度百分比？

单一分数很难告诉用户风险来自数据过期、口径混杂还是推断强度。方案展示可核验的客观信号，让用户知道问题在哪里，也知道下一步能做什么。

### 为什么需要版本对比？

纠正口径可能同时改变数值、原因排序和行动建议。保留 v1 可以防止答案被静默覆盖，v2 则说明修改造成了哪些变化，便于复盘和审计。

### “局部重跑”在原型里是真的吗？

当前是固定数据驱动的交互模拟，用来验证产品流程，不连接真实执行引擎。生产实现可以把结论绑定到查询、筛选条件和依赖节点，条件变更后只重新执行受影响的节点，并保存答案版本。

### 如何接入现有 Dora？

可以复用现有的思考过程、工具步骤、SQL 明细和最佳实践引用。新增的前台层需要四类结构化信息：结论标识、证据引用、条件依赖和版本差异。后端能力不必推倒重做，重点是把已有信息按结论重新组织。

### 为什么选择经营分析场景？

利润归因会同时涉及数据时效、门店范围、指标口径、事实与推断，以及建议是否可执行。一条故事线就能覆盖赛题关心的判断、追溯和纠错。

### 方案最大的风险是什么？

业务用户可能没有耐心主动核验证据。因此默认态先给出可信摘要和异常提醒，证据只在用户对某条结论产生疑问时展开。这个假设仍需要通过真实任务测试确认。

### 你做了哪些工作？

> 我完成了问题研究、Dora 现状审计、交互方案、视觉设计、React 原型、响应式适配、异常状态和演示材料。原型的数据与执行过程均为明确标注的 Mock，不把未实施的后端能力描述成已完成。
